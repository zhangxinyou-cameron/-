# 从 Git 仓库更新知习

0.4.0 起内置“软件更新”插件，默认启用。程序启动约 8 秒后检查一次，以后每 10 分钟检查一次；也可随时点左下角“检查软件更新”。检查在后台执行，不阻塞启动。

检测比较当前打包程序记录的 Git 提交与仓库 main（没有 main 时用 master），不依赖手工修改版本号。优先访问 Gitee，无法访问时尝试 GitHub；两个仓库的同步仍按项目约定维护。

## 使用

1. 左下角显示“发现新版本 · 可更新”后点击，即开始同步与构建。详情显示当前/远程提交、阶段进度及错误。
2. 更新器确认本地 main/master 无未提交内容，备份学习数据，获取最新提交，仅以 fast-forward 同步本地主分支。
3. 使用本机 Node.js/npm 执行 npm ci、准备资源、构建和打包。新版写入运行目录旁独立的暂存目录，正在使用的程序保持可运行。
4. 显示“重启完成更新”后点击。后台 Windows 助手等原程序退出，再切换整个程序目录并启动新版；原目录保留为备份。当前正在做题的草稿先保存，未保存的章节编辑或仍在运行的代码会阻止切换。

学习数据库继续使用原数据目录，不随程序目录移动。更新前的学习备份位于数据目录 updates/ 下。目录切换或新版 EXE 启动失败时助手尝试恢复原目录；若文件被外部程序锁定，会保留原程序及错误结果。此回退针对目录切换和进程启动，不承诺自动诊断新版进入界面后发生的所有错误。

## 环境与仓库

需要 Windows、Git、Node.js 24+、npm，以及能访问代码仓库和 npm/Electron 下载源的网络。首次安装构建依赖可能需要几分钟，阶段百分比表示实际步骤，不是下载字节百分比。

工作区内的知习会向上查找关联的项目仓库。独立解压的便携包需先准备知习源码克隆，再在更新详情中“关联本地源码仓库”。只接受包含 tech-practice/package.json 且远程指向本项目 Gitee/GitHub 的仓库。源码开发模式可检查更新，执行自更新需打开打包版 EXE。

更新器不会自动 stash、reset、强制覆盖本地主分支或推送远程。本地有未提交/未跟踪文件、正在特性分支、分叉或本地领先时，先自行提交或整合。依赖安装/构建失败时，源码可能已经快进到新提交，但原打包程序不替换；处理错误后可重试构建。

插件开关位于“插件管理 → 软件更新”。关闭隐藏入口并停止定时检查；同步构建或待切换期间不能关闭插件。普通桌面测试默认禁用真实联网检查，更新界面测试使用模拟服务，真实 Git、npm 和 Windows 助手测试在隔离夹具中执行。

## 后续 AI 修改入口

- desktop/updater.mjs：仓库发现、提交检测、快进同步、构建、阶段状态与路径校验。
- desktop/plugins/updates.mjs：更新插件接口；宿主只向可信内置插件提供 updater 服务。
- src/UpdateNotice.tsx：左下角按钮、定时检查与详情。
- desktop/install-update.ps1：退出后的目录切换、启动及失败恢复；保持 ASCII 脚本文本兼容 Windows PowerShell 5.1。
- scripts/package.mjs：写入 build-info.json，支持 TECH_PRACTICE_PACKAGE_DIR 暂存目标；暂存构建不能覆盖当前运行版或根启动器。后续修改打包器须保留这一契约。
- tests/updater.test.mjs、tests/updates-ui.mjs：运行与界面验证。不得通过真实用户仓库的 reset/强推制造测试场景。

旧程序备份与失败暂存目录以 .wisdom-backup- / .wisdom-update- 开头，与安装目录同级；本版保留这些文件，不自动清理。确认更新正常后可由用户管理磁盘占用。

实现参考：[Node 子进程 API](https://nodejs.org/api/child_process.html)、[Electron 应用生命周期](https://www.electronjs.org/docs/latest/api/app)。本项目采用独立 Windows 助手切换目录，不使用应用商店或 Electron autoUpdater 发布服务。
